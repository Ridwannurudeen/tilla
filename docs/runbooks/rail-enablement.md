# Tilla — dormant-rail enablement runbook (PREPARE-ONLY)

Every payment rail ships **flag-OFF**. This runbook is the exact, per-rail procedure to turn one
on. It is **user-run only** — an agent never flips a live flag, edits the VPS `.env`, moves funds,
or marks a settlement. Flag names below are verified against `app/config.py` on this trunk.

## The one procedure (every rail, no exceptions)

1. **Read-only probe first.** Confirm the dependency is reachable before enabling logic — the pattern
   the codebase already uses for `AGGR_DEFERRED`. For x402 rails that means the facilitator's
   read-only support check; for `ATTEST` it means the attest RPC is reachable. Confirm the exact
   probe call in the rail's module before relying on it.
2. **Set the flag + creds in the VPS `.env` only** (`/opt/tilla/.env`) — never in the repo, logs, or
   output. Restart the app so config reloads.
3. **One real funded settlement.** A single arm's-length test from Tilla's dedicated buyer wallet to a
   real merchant wallet — exactly one send, verified with a read call (never re-send to "check").
4. **Record it in `docs/PROOF-onchain.md`** in the existing format (tx hash, block, receipt status,
   wallets labeled arm's-length). Public numbers are generated by code, never typed.
5. **Never bulk-flip.** One rail, one proof, at a time. A rail stays labeled dormant until step 4 exists.

## Turnkey command sequence (mechanics verified from code + `docs/OPS.md`)

Config is `/opt/tilla/.env` on the VPS (`root@75.119.153.252`, code at `/opt/tilla`, systemd unit
`tilla-api`). The `.env` is **server-owned** — `scripts/deploy.sh` never writes it. Flipping a flag =
edit that file + restart. Every `[YOU]` / `[FUNDS]` step runs as root on the VPS and **cannot be
automated by an agent**; the `[verify]`/`[probe]` steps are read-only.

**Generic per-rail sequence**
1. `[probe]` For x402 rails, confirm the facilitator lists the scheme first. The app already runs a
   boot-time `_probe_supported()` (`app/main.py`); `app/config.py:182` warns to flip `aggr_deferred`
   only *after* `/supported` confirms it. Check the current `/supported` result before enabling.
2. `[YOU]` Add the rail's env line(s) to `/opt/tilla/.env` (values are yours; secrets never leave the VPS).
3. `[YOU]` `systemctl restart tilla-api` (systemd `Restart=always`; `/ready` may `503` for ~30s until the
   first sweeper tick — expected).
4. `[verify]` `curl -s https://tilla.gudman.xyz/ready` → `200` (DB + migration head + sweeper/RPC fresh).
   The migration-head check is **dynamic** — `db.expected_migration_head()` reads the alembic scripts and
   compares to the DB's applied head — so it auto-matches the deployed head (`0027_commission_jobs`) once
   you migrate. (`OPS.md`'s `0008_onchain_receipts` is a stale example, not a hardcoded value.)
5. `[FUNDS]` One real arm's-length settlement over the rail — **exactly one send**, verified with a read
   call (`GET /api/checkout/<id>` + an independent `eth_getTransactionReceipt`), never a re-send to "check".
6. `[record]` Append the tx to `docs/PROOF-onchain.md` in the existing format (labeled arm's-length).

## Escrow — custody note (read before enabling `TILLA_ESCROW`)

Escrow is the only custodial-adjacent surface, so it is opt-in and its flag stays OFF until you decide
the custody model. **Even enabled, Tilla holds no keys and sends no funds.** The `funded` and
`completed` transitions only *verify and record* a user-signed on-chain transfer (the same verify-only
pattern as `self_serve`/`refunds`). Enabling the flag exposes the job-lifecycle API; the parties (or an
`evaluator_addr`) sign the actual `buyer → escrow_addr` deposit and `escrow_addr → provider` release
themselves. There is no code path that moves funds — confirmed by a source-level test in the module.
